# Business rules

Rules below describe implemented behavior unless explicitly marked as a gap. They are not proposed commercial changes.

| ID | Rule and evidence | Consequence / limitation |
| --- | --- | --- |
| RN-001 | Clinic tenant; active authenticated user; ADMIN/PATIENT have no clinic, OWNER/DENTIST/ASSISTANT have one. AccessPolicyService, JWT strategy, route guards, SQL user-role constraint. | ADMIN is not a super-owner of clinical records. Cross-tenant IDs must be scoped; UI visibility is not authorization. |
| RN-002 | Access JWT validated with HS256, DB user state/tokenVersion; refresh opaque token SHA-256 hash, rotation and reuse revocation. auth.service, jwt.strategy. | Refresh theft/reuse can revoke all refresh sessions; tokenVersion invalidates access where incremented. No universal immediate JWT revocation from merely removing a refresh cookie. |
| RN-003 | Password bcrypt cost 12; login identity failure limit 8/15 minutes plus route/IP throttling. Reset token one hour; generic request response; conditional one-time claim inside the password/session transaction. | Memory counters are per instance; Resend key and sender are mandatory at production boot; actual delivery still needs verification. |
| RN-004 | Registration establishes clinic owner and terms acceptance; Google creates provisional PATIENT until complete-profile. OAuth state expires and is consumed. | PATIENT is not an end-user clinical role. Version strings in frontend/company and backend/auth must stay aligned. |
| RN-005 | One active owner per clinic via SQL partial unique index; active nondeleted clinic users count against Plan.maxUsersPerClinic. Seed 8/16/24. | Nullable maxProfiles/maxServicesPerProfile are not enforced. Downgrade behavior for already excessive usage needs explicit acceptance criteria. |
| RN-006 | DENTIST actions are scoped to own profile where policy requires; OWNER/ASSISTANT perform allowed clinic scheduling. Public profile reads require published data. | No role hierarchy or automatic public appointment-booking UI. |
| RN-007 | Appointment interval/status checks and PostgreSQL advisory transaction lock serialize creation for clinic/profile/day. Brazil date helpers preserve calendar boundaries. | Prove concurrency against PostgreSQL; mocks cannot validate locking semantics. |
| RN-008 | Patient identity is `Patient.id`, a clinic-scoped surrogate key. Name, email, phone and CPF are attributes and are never unique: two people may share all of them. Explicit IDs dominate; conflicting legacy identifiers fail. Centralized compatibility rejects ambiguity and uses a resolved stable ID or limits access to `patientId IS NULL`; direct contact matching must never mutate stable-owned clinical data. Completion snapshots, history, timeline, attention and avatar state remain Patient-scoped. | Identity must be asserted by the operator (selecting or explicitly creating a patient), never inferred for new bookings from matching contact details. Backfill propagates only an established appointment identity with matching record/appointment/Patient clinics, locking and revalidating that proof in the write transaction. Unprovable or changed relationships remain quarantined. |
| RN-009 | Appointment payments and finance entries use authorized roles and integer cents; uniqueness on clinic/appointment/source and clinic/fixedExpense/dueDate prevents duplicates. | SaaS Stripe subscription billing is separate from clinic receivables; no Stripe patient-payment workflow is implied. |
| RN-010 | Clinical drafts/status changes, events, attachments, templates and odontogram are controlled by clinic/professional access. Dictation structures draft input. | Not a qualified digital signature or autonomous diagnosis. Human review and reliable patient matching remain mandatory product boundaries. |
| RN-011 | Stock operations track movements and authorized category/product associations, with persisted balance changes. | Deactivation is not universal deletion. Physical inventory reconciliation remains an operational task. |
| RN-012 | LocalFiscalInvoiceProvider emits SIMULATED / SEM-VALIDADE identifiers and legalValidity=false. | No valid NFS-e, external cancellation, provider PDF or XML is implemented. |
| RN-013 | Trial seven days once according to trialEndsAt; paid state from Stripe; plan change creates prorations; cancel at period end. ACTIVE allowed; TRIALING requires future trial end; CANCELED allowed until paid period end; PAST_DUE/UNPAID/INCOMPLETE/PAUSED blocked. | Changes are not universally scheduled for next cycle. Failed webhook processing returns 503; a PostgreSQL transaction/advisory lock serializes event processing and atomic local changes. Current Stripe state/price replaces stale update/invoice data; strict subscription/customer matching protects replacements. This is not exactly-once external delivery. |
| RN-014 | Clinical dictation is Premium-only; Starter/Professional report zero effective dictation quota. AI quotas depend on plan/type/month; WhatsApp fallback quotas 0/50/300 and consent/template checks. Notification quota reserved atomically before sending, released on immediate failure. | Provider acceptance is not final delivery. Async FAILED receipts do not establish quota refund. AI quota check/count is not proof of atomic reservation under concurrent calls. |
| RN-015 | Privacy administration/audit reads are ADMIN-only. Consent and terms versions are recorded; privacy requests are workflow records. | No general erasure/export pipeline or timed retention job is established; scalar audit/subject IDs are not all enforced FKs. |
| RN-016 | Calendar OAuth tokens encrypted with configured secret; owner clinic and dentist user connections; outbound sync. | Login OAuth is separate. No implemented privacy-mode selector or general inbound reconciliation should be promised. |
| RN-017 | Public pricing/capability content is static while checkout uses backend catalogue and Stripe price IDs. | Marketing amounts, expired promotions and feature descriptions require reconciliation; a support/custom-domain boolean does not prove service delivery. |
